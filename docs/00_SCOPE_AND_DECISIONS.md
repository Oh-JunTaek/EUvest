# 00 — 확정 요구사항 및 범위 통제

## A. 프로젝트 정체성
사용자 본인만의 개인 실험: 소액을 KIS 본인 계좌에서 투자하는 **자율 투자 AI**를 만들어 사람이 직접 선택한 상품 또는 단순 ETF 보유보다 나은 성과를 내는지 객관적으로 검증. 수익 보장 없음. 자동매매는 현재 이 프로젝트의 **핵심 목적**이며, 과거 공개 투자 교육 서비스의 자동매매 제외 정책은 이 개인 실험에 적용하지 않는다.

## B. 확정 사항 (코딩 에이전트가 질문 없이 따라야 함)
1. **개발 에이전트는 OpenRouter**를 사용한다. 투자 판단 AI와 동일하지 않다.
2. 실제 투자 추론은 **모델·공급자 교체 가능**: 무료 API (NVIDIA NIM은 후보일 뿐) 또는 데스크톱 로컬 Ollama. 외부 무료 API는 라이선스·접속 보장·보존 정책 확인 전 `LIVE` 금지. 휴대폰 Gemma E2B는 후순위 실험.
3. KIS Open API 고정. 해외/국내 시장 토글 독립; KRX와 미국 주식시장 양쪽 가능. 종목은 사용자가 거래 허용 목록에 넣어야 한다. 빈 목록은 거래 금지.
4. 상품은 국내외 현물주식/ETF 초기, 국내 장내채권은 공식 기능 확인 후 추가, 해외 채권은 지원 확인 전 표시만. 파생상품은 초기 범위 밖.
5. 사용 가능한 현금 및 보유 수량 외 매매 금지. **신용·미수·대출·공매도 불가**. 레버리지/인버스 ETF는 구조적으로 `is_leveraged`/`restricted` 정보 저장하되 기본 차단, 실거래 허용은 별도 승인.
6. 한 번 계좌에 자금이 입금되면 계좌 현금 한도를 인식. 모든 돈 투자 의무 없음. AI는 매수/매도/보유/아무 거래 없음과 현금 100% 유지 가능.
7. 매매 주기 사용자가 설정 가능. PC 켜져 있을 때만 실행하는 Windows 로컬 스케줄러가 기본. PC OFF일 때 외부 LLM API만으로 주문이 실행되지는 않는다.
8. **사용자 개입은 최소화**: 사용자는 거래 가능 범위·API·리스크 상한·실거래 활성화만 설정; 개별 매매 승인 버튼을 매번 누르게 만들지 않는다. 초기 실거래 활성화는 사용자가 직접 승인.
9. 분석·판단·주문·체결·성과 평가 모두 기록. 모델 교체/재시작해도 가설과 미체결 상태 인계. 투자 결과는 시장 단순 보유 및 다른 전략과 비교.
10. 기능 우선. UI는 Python CLI, 로그/상태 보고서로 충분. 로그인·프런트엔드·서버·클라우드·회원가입 불필요.
11. 개발 순서: 사양/API 조사 → 오프라인 모의 → KIS 읽기전용 → KIS 모의 → AI 통합 → 스케줄링/평가 → 사용자가 승인하는 LIVE → 휴대폰/채권 확장. 매 단계 독립 검증.

## C. 구현 시 반드시 구분할 4개 실행 모드
- `BACKTEST`: 과거 OHLCV·시점별 뉴스/공시 스냅샷, 미래 정보 누출 방지. 백테스트 가능 범위 확인 전 AI 과거뉴스 예측력 주장 금지.
- `OFFLINE_SIM`: 네트워크 없이 기록된/샘플 데이터와 MockBroker로 시뮬레이션. **기본 모드**. CI 및 자동 테스트.
- `KIS_PAPER`: KIS 공식 모의계좌에서 지원되는 자산에 한해 모의 주문. 지원 미확인 기능은 `UNSUPPORTED`.
- `LIVE`: 본인 실제 계좌에 실주문. 사용자 명시적 승인/모든 보호·검증 완료 전 전환 불가.

## D. 전략 자율성 vs 강제 안전의 구분
| AI에게 맡김 | 별도 엔진이 강제 |
|---|---|
| 거래 여부, 조사 우선순위, 종목별 목표 비중, 투자 기간/가설 | 거래 허용 상품, 실제 현금·보유량, 주문단위·시장시간, 리스크 하드캡 |
| 시장 불안정 평가, 0~100% 현금 보유, 거래하지 않기 | 계좌/미체결 동기화, 데이터 시점, 환전비·세금·수수료 계산, 오류·장애 중지 |
| 과거 판단 근거를 뒤집을지 결정 | 재판단 사유 보존, 데이터 검증, 모든 주문 추적·중복 차단 |

- 거래 횟수 최소화는 목적이지만 `매 시간 반드시 거래` 또는 `매도 후 N시간 무조건 대기` 같은 **전략 규칙은 AI를 대신해 고정하지 않는다**. 거래 경제성 비용 검증과 신용/현금 제한은 예외.
- 사용자 리스크 하드캡(단일 주문 한도/일 손실 중지/전체 총 노출)은 실거래에 필요한 계좌 안전 통제이며 구체 숫자는 사용자 승인 전 `LIVE_BLOCKED`.

## E. 초기 구현 우선순위
- **P0**: 모드 격리, KRX/US 토글, allowlist, 환율·현금 장부·계좌 동기화, 안전 주문 상태기계, 모의 broker, AI 인터페이스 + 영속 상태, 실패 복구, 기초 성과 평가, CLI, 회귀 테스트.
- **P1**: 뉴스/공시·기업 이벤트 조사, KIS paper 주문, 스케줄러, 비교 리포트, 계좌 이벤트/입출금 처리, 복수 모델 교체.
- **P2**: 국내 채권 실주문, 해외 채권, Android Gemma, 레버리지 ETF 사용자 별도 허용, UI 보강.

## F. 절대 임의 확정하면 안 되는 것
- 계좌번호, 비밀번호, API/LLM 키, 실제 자본, 수수료, 원화/달러 환전 방식, 실거래 손실 허용치, 주문 실행 시장·세션(정규장/시간외), 외부 API 이용약관의 실거래 허용 여부, 신용 거래를 허용하는 주문 필드.
- 문서 11의 `BLOCKING_LIVE`만 **실거래 전에** 결정받고, 나머지는 안전한 기본값으로 구현한다. 사양이 미확정이어도 OFFLINE_SIM/PAPER 개발을 중단하지 말 것.
