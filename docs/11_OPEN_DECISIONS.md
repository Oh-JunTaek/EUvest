## 처음 사용자에게 물어볼 4가지 (대답을 기다리되 개발 전체를 막지 말 것)
1. 최초 PAPER 실험 허용 종목은 KRX 1~2개와 미국 ETF 1~2개처럼 제한할까, 직접 목록을 넣을까? (현재 빈 목록 유지)
2. 첫 운영 모델은 로컬 Ollama부터 시험할지, 무료 원격 API를 먼저 시험할지? (둘 다 구현, 기본 Fake)
3. 자동 실험 실행 주기는 매 60분을 기본값으로 둘까, 시장별 정규장 시작·종료 시점에 하루 2회로 둘까? (기본 스케줄 OFF)
4. 미국 주식은 보유 USD만 사용하고 자동 환전은 일단 제외할까? (안전 기본값 OFF)

## 실거래 활성화 직전에 반드시 사용자에게 재질문할 것
- 실거래에 할당할 전용 계좌와 현금 자본, 허용 자산 목록
- 하루 손실/월 최대 낙폭, 단일 주문 금액, 계좌 전체 노출 최대치
- 미국 주식 환전·세금·수수료와 채권 거래 관련 추가 확인
- 사용하고자 하는 운영 LLM 공급자의 실제 거래 사용 허가 여부와 개인정보 정책
- 계좌 연결 및 종목별 PAPER 통합 검증 수행 여부

## 사용자가 변경하면 안 되는 강제 제한
`cash_only=true`, `no_margin=true`, `no_short=true`, `no_auto_credit=true`는 개발팀 임의 완화 불가. 사용자가 나중에 레버리지 ETF 매수를 허용하더라도 **신용/미수 주문 허용과 별개**이며 기본 설정은 여전히 OFF.

## 구현·명세 충돌 — P0-03 기존 데이터 이행

**P03-DATA-01 (결정됨, 2026-11-04):** 현재 v1/v2 `theses`는 단일 `id`, `hypothesis`, `rationale`을 저장하지만 문서 03은 `(thesis_id, version)`, `premise`, `invalidation` 등 이력 필드를 요구한다. 기존 `decisions`, `handoffs`, `agent_runs`도 필수 계약과 이름·내용·키가 다르다. 기존 기록의 가설 버전·무효화 조건·state_version·주문 intent 관계를 추론할 근거가 없다. 과거 naive timestamp와 짧은 asset_id도 실제 시간대·거래소·상품유형을 확정할 수 없다.

영향: 자동 매핑하거나 이전 데이터를 삭제하면 투자 판단·주문 이력 의미가 변할 수 있다. 사용자의 아래 결정에 따라 두 DB는 보존하고 신규 계약 DB를 빈 상태로 사용한다. 추후 실제 이행을 원할 때는 DB 사본과 백업 복원 리허설, 필드별 출처·변환 규칙 및 불명 값 처리에 대한 별도 결정이 필요하다. 이 결정이 LIVE 또는 실제 주문 승인을 뜻하지 않는다.

**2026-11-04 진행:** 사용자의 P0-03 계속 요청에 따라 기존 DB를 변경하지 않는 별도 신규 계약 DB를 작성했다. 과거 이력의 값 매핑 및 실제 이행은 여전히 결정·검증되지 않았다. 기존 저장소가 신규 계약 DB를 자동으로 사용하지 않으므로 양쪽을 연결하기 전 P0-03 전체 완료로 판단하지 않는다.

**2026-11-04 사용자 결정:** `data/test.db`와 `data/test2.db`는 그대로 보존하고 신규 DB를 빈 상태로 시작한다. 각 DB에는 가설 1건, 판단·주문 0건이 있었다(읽기 전용 집계). 기존 가설을 신규 계약으로 변환하지 않는다. 이 결정은 기존 DB 삭제, 실계좌 연결, 실제 주문 또는 LIVE 승인이 아니다.

**P03-ACCEPT-01 (결정됨, 2026-11-04):** 사용자 승인으로 P0-03은 저장 계층 인수를 완료하고, T-018의 중복 실행·broker 주문 횟수와 T-035의 손상 DB에서 실제 거래 차단은 실행기·브로커가 구현된 후 필수 통합 검증으로 이월한다. 저장 계층의 충돌·손상 거부 결과를 이 통합 검증의 통과로 간주하지 않는다. T-025도 저장 계층 stale 거부만 확인했으므로 실제 주문 경계 검증은 후속 작업에 남긴다.

## P1-10 연동 전 기존 구현 충돌 — 2026-11-07

아래는 사용자 전략 결정을 요구하는 항목이 아니라 구현·명세 불일치다. 안전한 실행을 연결하기 전에 각각 이전 티켓 범위에서 수정·테스트한다. 세부 재현과 근거는 `P09_P10_READINESS_2026-11-07.md` 참조.

- **P10-BLOCK-01 / P0-06:** 주문 상태 전이가 없는 enum 값을 참조하여 예외를 내며, 부분체결 수량 중복 증가·상태표 불일치, 환율 변환 방향 및 현금/보유 초과 방지에 결함이 있다. 임의 LIVE 한도도 사용자 승인값이 아니다. 기존 엔진을 주문 경로에 연결하지 않는다.
- **P10-BLOCK-02 / P0-07:** FakeProvider의 frozen 응답을 라우터가 직접 수정해 실패한다. fallback 설정·입력 비밀 검증도 별도 점검이 필요하다. 수정·검증 전 모델 라우터를 실행기에 연결하지 않는다.
- **P10-BLOCK-03 / P0-08:** `ContextBuilder`가 존재하지 않는 저장소 메서드를 호출하고 구 저장소 스키마를 사용한다. 새 `contract_store`/`data/investor.db`와 자동 호환되지 않는다. 가설·미체결·민감정보 인계 경계의 통합 검증이 선행되어야 한다.
- **P10-BLOCK-04 / P1-09:** OpenDART 실제 네트워크 조회는 인증키 URL 로그 노출 가능성 때문에 코드에서 차단했다. 공시 목록은 날짜만 제공하며, 회사 고유번호 매핑·발표 시각·ZIP 처리·구 Evidence와 신규 저장 계약의 연결은 미완료다. 조사 실패나 UNSUPPORTED를 NO_TRADE 성공으로 바꾸지 않는다.
